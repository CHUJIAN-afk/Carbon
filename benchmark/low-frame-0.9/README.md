# 0.9 长帧定位

本次静止场景的长帧不能归结为缓存更新。没有重建的窗口仍出现 14.5753 ms 长帧，对应 JFR 记录到 12.3838 ms 的 GC Remark 停顿。较低外部负载下，强制重建的缓存更新时间 p95 为 0.4164 ms，最长帧为 9.7030 ms，其中缓存更新只有 0.3747 ms，附近的 GC Remark 为 7.4457 ms。

## 条件与采样

Intel Core i7-12800HX、RTX 4070 Laptop GPU，JBR 21.0.11；Minecraft 1.21.1、NeoForge 21.1.238、Sodium 0.6.13、Iris 1.8.12。性能定位时关闭光影，1920×1080、FOV 70、视距 4 区块、隐藏窗口、关闭垂直同步，帧率上限选项 260 对应无限制。

1000 个实体处于地面，每个物品数量为 64，五种物品等量混合：钻石剑、橡木木板、钻石、铁锭、玻璃。专用管线收集 1000 个实体，共 5000 个模型副本、1536 个圆形阴影实例。玩家固定在 `(0,200,14.8)`，yaw 180°、pitch 0°，最近水平距离 11 格。客户端与服务端实体 tick 冻结；产品代码没有冻结专用快速路径。冻结后仍有输入、GUI、网络、乘客判断等客户端或服务端管理成本。

开启物理化与跳过可见性检查，缓存预算 2 ms。每段采集 20 秒，记录每帧缓存、收集、绘制、上传和客户端 tick 耗时，并用 JFR 采样执行栈、原生调用和 GC。诊断性强制重建每 50 ms 标记场景失效，用于单独观察更新成本，不代表自然过期行为。

三段产品代码相同。早期静止与强制重建窗口的 JFR 整机平均 CPU 负载分别约 25.8%、38.7%，且早期进程监控未完整覆盖强制重建窗口；该强制样本的 46.63 ms 最大帧不作为最终性能成绩。后续低干扰窗口重新采样，并将测试控制文件的轮询由每帧降为每 50 ms，减少探针开销。**这些窗口不是代码优化前后对照，不能用其 FPS 差异宣称性能提升。**

## 低干扰窗口结果

| 指标 | 数值 |
| --- | ---: |
| 采样帧数 | 13,533 |
| 平均 FPS | 676.72 |
| 1% low / 0.1% low | 353.70 / 151.82 FPS |
| 帧时间 p50 / p95 / p99 | 1.4207 / 1.8316 / 2.1639 ms |
| 最长帧 | 9.7030 ms |
| 缓存更新帧数 / 总处理实体数 | 394 / 394,000 |
| 活跃更新帧缓存 p50 / p95 / p99 / 最大值 | 0.2846 / 0.4164 / 0.5411 / 1.4005 ms |
| 完整收集 p95 / 最大值 | 0.4495 / 1.4537 ms |
| 单帧实例上传函数 p99 / 最大值 | 0.0213 / 0.3365 ms |

平均 FPS 为帧数除以累计帧间隔；1% / 0.1% low 为最慢 `ceil(帧数×比例)` 帧的平均时间取倒数。实例上传指标不包含独立的阴影上传；GPU 异步执行成本也不能由 CPU 函数时长直接推断。

每约 2 秒记录进程与 GPU 状态，窗口内使用 10 个有效样本。游戏 CPU 平均为单核等效 56.24%，最大 81.66%；其他进程合计平均 60.45%、最大 115.73%。100% 表示一个逻辑核心，不是整机总量。JFR 整机平均 CPU 负载为 7.58%；GPU 利用率 61–68%，图形时钟保持 2490 MHz，温度 62–63°C，功耗 28.35–28.74 W。仍有桌面应用负载，本次只能作为单机诊断样本。

## 瓶颈证据

- 静止窗口 11,377 帧均未处理缓存更新，仍出现 14.58 ms 长帧，说明移动缓存更新位置不能消除全部长帧。
- 低干扰窗口记录到 2.44–7.45 ms 的 GC 暂停，多个长帧与这些暂停对齐。最长帧中缓存更新只占约 0.375 ms；另一个 7.8165 ms 长帧没有缓存更新，绘制阶段记录 6.0889 ms，但附近有 5.6897 ms GC，不能把整个绘制阶段时间归因于 GPU 或 Carbon 绘制。
- 分配采样过滤每线程首个样本及开始 2 秒后，`Vec3` 占分配采样权重约 48.36%，主要调用链为 `CubicSampler.gaussianSampleVec3`、天空颜色与雾色计算。冻结状态的 `countPlayerPassengers()` stream 也有分配；这属于诊断环境成本，不据此加入冻结快速路径。
- Carbon 绘制调用中的 `ShaderInstance.setDefaultUniforms()` 也出现在分配热点，重复构造 sampler 名称等对象；它的两条主要字符串分配栈合计约占分配采样权重 2.69%，优先级低于天空、雾色路径。
- 低干扰窗口约 78.5% 的渲染线程执行/原生混合样本位于 `glfwSwapBuffers`。这反映提交或等待位置，不能直接解释为 GPU 计算耗时占比；没有 GPU 时间线时无法进一步区分驱动、合成器和调度等待。

JFR 样本权重不是精确分配字节、CPU 时间比例或节省潜力。GC 对齐数据按帧结束事件重建时间区间，边界可能受探针记录开销影响；原始 CSV 与 JFR 保存在本地 `build/ui09/results/`。公开摘要见 [results.json](results.json)，采样栈见 [focused-force-profile.txt](focused-force-profile.txt)。

## 缓存更新方向评估

| 方向 | 可能收益 | 约束 |
| --- | --- | --- |
| 客户端物品实体 tick 更新 | 复用本 tick 已计算的姿态、资格、组件与运动信息，减少渲染阶段重复查询 | tick 与渲染运行在同一客户端主线程。1000 个实体集中于同一 tick 处理仍会制造长帧；相机、可见性与帧内插值不能直接按 tick 固定。应保留按帧预算，并分别处理状态变更和场景拓扑变化。 |
| 独立线程异步更新 | 将不可变快照的纯姿态计算、实例字节生成移出主线程 | 当前重建读取实体、组件、世界光照、模型和扩展接口，并可能创建 OpenGL 资源，不能直接把 `collect()` 或 `submitEntity()` 放到线程池。需要主线程采样、工作线程处理独立缓冲、主线程校验资源代次并交换；首次模型捕获和 GPU 操作仍留在渲染线程。 |

后续优先项为减少实际分配、量化呈现等待；缓存侧优先研究逐实体脏记录与局部实例更新，避免一个实体变化触发整场景扫描。已有实体资格、组件版本、运动状态、方块光照和阴影接收面缓存可以继续利用。异步化仅适合确认仍占主要时间的快照计算，不能消除 GC 停顿，也不应以转移同一主线程上的工作代替减少总工作量。

本次只完成瓶颈定位，未改变缓存调度架构，也未加入冻结专用路径。
